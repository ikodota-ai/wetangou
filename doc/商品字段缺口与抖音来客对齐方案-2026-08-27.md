### 1.1 抖音来客后台商品「查看态」是独立页面
- 7 区块固定顺序：**商品类型 → 商家信息 → 商品信息 → 售卖信息 → 交易规则 → 消费规则 → 商品资质**
- 每屏底部固定「编辑」按钮，右上「预览」（顾客视角）
- 不是编辑页 disabled，是**独立只读页**（两个商品类型交叉验证，版式一致）

### 1.2 交易规则 / 投放渠道 / 商品搭配都是独立子页 + 底部提交
- 四种行型：① 跳转行`>` ② **开关渐进**（先开关、开了才展开细则）③ 字段级灰字说明 ④ 同行可填
- 我们 `create.vue` 只有第 ④ 种，纯 inline 单层平铺，**一个字段级说明文案都没有**
- 投放渠道是**分组列表 + 底部确认**，每渠道有独立投放规则说明 → 有真实业务语义，不是装饰字段
- 商品搭配：**分组卡 + 组内子品 + 组内"N选M"** → 与我们本轮已实装模型**一致，无需返工**

### 1.3 顾客端详情 IA 终稿（20 屏交叉验证）
1 大图/轮播 → 2 价格条（大售价 + 划线原价） → 3 主标题 + **副标题灰字** → 4 **套餐明细卡（条目 + 尾部"合计/总价值"加重行）** → 5 两列式规则行密集卡 → 6 **大段图文说明块** → 7 适用门店列表卡 → 8 更多商品推荐 → 9 尾屏再一个说明块

- **20 屏全部无吸顶导航** → 顾客端浏览态确定不做吸顶（与我们现状一致，非缺陷）
- c1/c2 完全同模板，不随 typeCode 换版式

### 1.4 评价体系（rev_360~364）
本项目**完全无此功能**（无表、无接口、无 wxml 区块）→ 属新增需求，归 P3。

## 二、三类缺口清单

### A. 后台填了但存不下（12 项）

| 区块 | 页面 label | 前端字段 | 根因 |
|---|---|---|---|
| 售卖信息 | 投放渠道 | `saleChannels` | Product 域无属性，Jackson 丢弃 |
| 售卖信息 | 职人带货 | `staffPromote` | 同上 |
| 售卖信息 | 商品售卖日期 | `saleDateRange` | **库里有** `sale_start_date`/`sale_end_date`，前端从没拆开传 |
| 交易规则 | 券码类型 | `codeType` | 无属性 |
| 交易规则 | 顾客可消费日期 | `consumeDateRange` | 无属性 |
| 交易规则 | 顾客不可消费日期 | `excludeDateRange` | 无属性 |
| 交易规则 | 每日消费时段 | `dailyTimeRange` | 无属性 |
| 消费规则 | 适用范围（代金券） | `scopeType` | 无属性（ext 有 `voucher_scope_type` 未接上） |
| 消费规则 | 店内其他优惠 | `storeOtherDiscount` | 主表**有** `mutexWithStorePromotion`，**名字不匹配** |
| 消费规则 | 额外费用 | `extraFee` | 主表**有** `extraFeeDesc`，**名字不匹配** |
| 商品资质 | 券类型 | `voucherType` | ext 有 `voucher_scope_type` 未接上 |
| 商品资质 | 适用规则 | `voucherRules` | 无属性 |

**数据佐证**：357 个商品中仅 35 个有 `sale_start_date`、**2 个**有 `extra_fee_desc` → 证明这两个框从未真正生效。

**两类性质**：
- **5 个「后端已有属性、前端没接对」**（`saleDateRange` / `extraFee` / `storeOtherDiscount` / `voucherType` / `scopeType`）→ 最划算，**纯前端字段映射**即可修复，零 DDL
- **7 个纯缺字段**（`saleChannels` / `staffPromote` / `codeType` / `consumeDateRange` / `excludeDateRange` / `dailyTimeRange` / `voucherRules`）→ 要么建列 + 加域字段，要么先隐藏表单项

### B. 存下来了但顾客端不渲染（5 项）

| 字段 | 现状 | 抖音对照证据 |
|---|---|---|
| `detail` 富文本 | `normalize` 里处理了，**wxml 从没渲染** | c1_344/348 + c2 尾段：说明块出现 ≥2 次 |
| `subtitle` | 不显示 | c1_340 / c2_349 首屏紧贴主标题有副标题位 |
| `comboTotalValue` | 后端有，前端无「合计/总价值」行 | c1_341/342 + c2_350 都有加重合计行 |
| `collectMethod` | 不显示 | detail_379 有「收款方式」行 |
| `consumeStartToday` / `mutexWithStorePromotion` | 不显示 | detail_382/383 有对应规则行 |

> 用户原话：「后台的一些设置应该给前端看到，否则设置了有什么意义呢？」

### C. 商家端（小程序）建品 vs 后台

| | 后台 | 商家端 |
|---|---|---|
| 字段数 | 33 | **21** |
| 分步 | 分段式 + 吸顶导航 7 区块 | 单页平铺 |
| 适用门店 | 多选 | **单选**（`storeIds: String(f.storeId)`）|
| 新建后状态 | 草稿（下架） | **直接 `status:'0'` 上架** |

**P0 缺陷：商家端「编辑」是坏的**
`list/index.js` 的 `onEdit` 跳 `create/index?productId=xxx`，但 `create/index.js` 的 `onLoad()` **完全没读 productId**，全文件只有 `productAdd`、无 `productUpdate` → 商家点编辑打开空表单，填完保存**新建一个重复商品**。另「改时间」仍是 `待实现` toast。

## 三、分优先级方案

### P0-1 商家端「编辑」误新建（数据损坏，必须先修）

**改动点**
1. `miniprogram7/pages/merchant/product/create/index.js`
   - `onLoad(q)` 读 `q.productId`；有值则 `GET /api/product/{id}` 回填表单，`data.mode='edit'`
   - 提交分流：`mode==='edit'` 走 `productUpdate`（需确认小程序端 API 是否已有；若无则新增，复用 admin `PUT /biz/product`）
   - 编辑态锁 `typeCode`（类型不允许改，与后台一致）
2. 兜底（若本轮不做编辑）：`list/index.js` 的 `onEdit` 直接 `showToast('请在后台编辑')`，**先断掉误建路径**

**验证**：商家端建品 → 列表点编辑 → 改名保存 → `SELECT count(*) FROM biz_product WHERE product_name LIKE '%xxx%'` 应为 1 条而非 2 条。

**工作量**：兜底 10 分钟；完整编辑 0.5 天。

---

### P0-2 12 个「填了即丢」字段（不能继续误导运营）

按「性价比」拆 3 档，建议全部做，因为每一档都很轻：

**档 1｜纯前端映射，零后端改动、零 DDL（今天就能上）**

已核实 `Product.java` 主表域**已有**这些属性，纯粹是前端字段名/结构没对上：

| 前端现状 | 后端已有属性（Product.java 行号） | 改法 |
|---|---|---|
| `saleDateRange` 数组 | `saleStartDate` L109 / `saleEndDate` L112 | 提交前拆成两个字段 |
| `extraFee` | `extraFeeDesc` L148 | 改前端字段名 |
| `storeOtherDiscount` | `mutexWithStorePromotion` L145 | 改前端字段名（语义同义：是否可与店内其他优惠同享） |
| `voucherType` / `scopeType` | `ext.voucherScopeType`（ProductExt 已有） | 统一接到 ext 该字段 |

> 5 个输入框立刻从「填了丢」变成「填了存」，**不需要任何 DDL、不需要改后端一行代码**。这是全部方案里性价比最高的一档。

**档 2｜值得补落库的（走 ProductExt，加 2 列）**
| 字段 | 建议列 | 理由 |
|---|---|---|
| `codeType` 券码类型 | `biz_product_ext.code_type` | 影响核销方式，真实业务语义 |
| `voucherRules` 适用规则 | `biz_product_ext.voucher_rules` | 代金券必填项（detail_379 逐字确认） |

> 放 `ProductExt`（已有 14 字段）而非 `biz_product`：避免踩「库表 DEFAULT 架空 null 校验」的陷阱（`price`/`stock`/`validityDays` 等已因 DEFAULT 导致 Validator 需用 `requirePositive` 特判）。

**档 3｜先隐藏 + 记「待实装」（不要建列）**
| 字段 | 处置 | 理由 |
|---|---|---|
| `saleChannels` 投放渠道 | 表单项 `v-if="false"` + 注释「待多渠道分发需求落地」 | chan_337/338 证明它有真实业务语义（分组 + 每渠道规则），但**当前无任何消费方**：顾客端不按渠道过滤、后端不按渠道路由。现在建列只会产生僵尸数据 |
| `staffPromote` 职人带货 | 同上 | 需要「职人」域（员工-带货关系表），远超本轮范围 |
| `consumeDateRange` / `excludeDateRange` / `dailyTimeRange` | 同上（**或**做 P2-1 的开关渐进后再开放） | 3 个日期/时段字段需要核销侧同步做时间校验，否则存了也不生效 |

**验证**：每档改完，后台填满 → `SELECT * FROM biz_product_ext WHERE product_id=?` 逐字段对账；隐藏项确认页面上看不到。

**工作量**：档 1 = 0.5 天；档 2 = 0.5 天（含 ext 加 2 列 + Validator）；档 3 = 1 小时。

## 五、拍板结论与本轮实测（2026-08-27 收口）

用户对第四节的 2 个建议**都否决了保守方案**，拍板为：

1. 12 个字段**全部补落库**（不接受"先隐藏"），并且**渠道要做成可收集的字典**而不是硬编码；
2. 商家端商品新增/编辑做**完整实装**（不做兜底断路）—— 理由是「商品新增编辑的主场景不在 PC，而在商家端」。

### 5.1 12 字段落库映射（已实测逐字段对账）

| 页面 label | 前端字段 | 落库位置 |
|---|---|---|
| 投放渠道 | `saleChannels` | `biz_product_ext.sale_channels` |
| 职人带货 | `staffPromote` | `biz_product_ext.staff_promote` |
| 商品售卖日期 | `saleDateRange[]` | 主表 `sale_start_date` / `sale_end_date`（列早就有，只是没人写） |
| 券码类型 | `codeType` | `biz_product_ext.code_type` |
| 顾客可消费日期 | `consumeDateRange[]` | `ext.consume_start_date` / `consume_end_date` |
| 顾客不可消费日期 | `excludeDateRange[]` | `ext.exclude_dates`（JSON `[[start,end]]`） |
| 每日消费时段 | `dailyTimeRange[]` | `ext.daily_time_start` / `daily_time_end` |
| 适用范围（代金券） | `scopeType` | `ext.voucher_scope_type` |
| 店内其他优惠 | `storeOtherDiscount` | 主表 `mutex_with_store_promotion`（**SHARE=0 / EXCLUSIVE=1，语义反转**） |
| 额外费用 | `extraFee` | 主表 `extra_fee_desc`（列早就有） |
| 券类型 | `voucherType` | `ext.voucher_scope_type`（与 scopeType 不同屏，互不覆盖） |
| 适用规则 | `voucherRules` | `ext.voucher_rules` |

**为什么放 ext 而不是主表**：主表加列必须给 DEFAULT，而 `biz_product` 已经因为
`price 0.00 / stock 0 / validity_days 30 / max_per_order 1` 这些 DEFAULT 架空了
null 校验 —— `ProductValidator` 不得不用 `requirePositive` 特判「填了 0 等于没填」。
再往主表加 9 个带 DEFAULT 的列只会让这个坑更大。

**渠道为什么不照抄抖音来客**：抖音来客的渠道是 DOUPIN / TOUTIAO 这类站内分发位，
与本项目（微信小程序生态）的实际投放场景无关。这个字段从上线起就没落过库，
没有存量兼容负担，所以按自有场景重定义为 5 个渠道（见 `biz_sale_channel` 种子）。

### 5.2 数据佐证（说明这些框从来没生效过）

357 个存量商品里：
- 只有 **2 个**有 `extra_fee_desc`
- 只有 **35 个**有 `sale_start_date`

这两列早就存在，说明不是"没建列"，而是前端填了根本没往这两列写。

### 5.3 本轮顺带修的真实缺陷

| # | 缺陷 | 根因 | 后果 |
|---|---|---|---|
| 1 | 小程序提交的 `ext` 被整个丢弃 | `ApiProductController.saveExtByTypeCode` 用 `new ProductExt()` 从零构造，没读 `body.getExt()` | 商家端传的渠道 / 券码类型 / 消费时段一个都存不进去。后台走 `ProductServiceImpl.saveExt`（读 body.ext）所以正常 —— 典型的「补了后台忘了小程序」 |
| 2 | 后台 `create.vue` 有两个同名 `watch` 块 | 对象字面量同名 key 后者覆盖前者 | 面值自动带出「xx 元代金券」从上线起就没生效过 |
| 3 | 商家端建品页 `onLoad` 不读 `productId` | 编辑入口传了参数但页面没接 | 点「编辑」进去是个空白新建页，改完变成新增一条 |
| 4 | 商家端建品页 5 个 `bindtap` 绑到不存在的 handler | `onPickStoreProxy` / `onTapDateField` / `onTapRuleField` / `onTapNumberField` / `onTapPeriodField` 在 js 里都没有 | 点了没反应，而且盖在 input 上挡住聚焦 |
| 5 | 商家端 `add` 无条件跑完整校验 | 与「先存草稿、补齐再上架」流程矛盾 | 商家填完名称+价格点「保存为草稿」被「GROUPON 需填库存 stock」顶回，草稿一条都存不下 |
| 6 | 商家端 `edit` 一个校验都没有 | admin 端的 `mergeOntoOrigin` 是 private static，跨模块复用不到 | 商家能把已上架商品的售价改成 0、库存改成 0，商品仍对顾客可见但下单必失败 |
| 7 | 商家端 `/api/product/status` 上架不校验 | 只查了 status 取值和商户归属 | 残缺草稿可以直接上架，顾客点进去下不了单 |
| 8 | 商家端列表页无上架入口 | 只有改时间 / 改库存 / 编辑 | 建品改草稿后，商家在小程序里永远上不了架，必须跑 PC 后台 |
| 9 | 商家端列表 tab 角标用当前页 filter 算 | 站在「已上架」tab 时请求带 `status=0`，返回的全是上架品 | 「已下架」角标恒为 0；商品超 20 条时上架角标也是错的 |
| 10 | 商家端列表照抄抖音摆了 3 个审核 tab | 本系统 `status` 只有 0 上架 / 1 下架，无审核流；点这 3 个 tab 时 status 传空串 | 返回的是「全部商品」，商家会以为有一堆商品卡在审核中 |

第 6 条的修法是把 `mergeOntoOrigin` / `isDraft` 从 admin 端 controller **下沉到
`ProductValidator`**，两端共用一套语义，而不是复制一份到小程序端。

### 5.4 实测结果

**12 字段写-读闭环**（造商品填满 12 字段 → SQL 逐字段对账 → 3 条读链路回读）：

- `biz_product`：`sale_start_date` / `sale_end_date` / `extra_fee_desc` /
  `mutex_with_store_promotion` 全部落库
- `biz_product_ext`：9 个新列全部落库，含 `exclude_dates` 的 JSON 和
  `daily_time_start/end` 的 `HH:mm:ss`
- 3 条读链路都带回 9 个新字段：admin 详情 `/biz/product/{id}`、
  admin 列表 `/biz/product/list`（走 `selectProductVo` 的 join）、
  小程序详情 `/api/product/{id}`（`data.ext`）

**商家端草稿流程**：
- 只填名称+价格 → 存草稿 200（原先被「需填库存」顶回）
- 残缺草稿上架 → 500「GROUPON 需填库存 stock」（指明缺哪个字段）
- 补齐 stock/validityDays/maxPerOrder → 上架 200

**校验与租户隔离**：
- 已上架商品把 stock 改 0 → 500 拦住（原先能存下）
- 已上架商品把 price 改 -1 → 500 拦住
- 只改 notice 的局部 PUT → 200 通过（不会因为没带 typeCode 被误判）
- 商户 1 店长改商户 2 商品 → 500「无权编辑该商品」
- 商户 1 店长上架商户 2 商品 → 500「无权操作该商品」
- 建品带别家门店 → 500「门店「测试02-春熙路店」不属于该商家」
- admin 端建草稿 / 上架行为无回归

`smoke-c1` 3/3、`smoke-subitem` / `smoke-e10` / `smoke-e4` PASS、
