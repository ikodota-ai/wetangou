# 推客功能恢复清单（2026-09-04 摘除）

## 为什么摘除

微信小程序第二轮审核驳回原文：

> 你好，小程序提现服务存在设置提现门槛，用户无法成功即时提现的情况，
> 请补充完善提现规则再提交代码审核。

用户反馈「线上环境推客入口是关闭的（`biz_merchant.promoter_enabled='0'`），
但审核员还是截到了提现页」。排查出**两个真 bug**，不是审核员用了特殊手段：

### bug 1：入口有异步窗口 + 请求失败时永久显示

`pages/mine/index/index.js` 里 `promoterEnabled` 初始值是 `true`，
原注释写着「接口没回来/请求失败时宁可显示入口」。而开关值来自
`app.js` 的 `bootMerchant()`，是**异步**的：

1. 进「我的」页 → `promoterEnabled=true` → **推客入口渲染出来**
2. `bootMerchant()` 回来 → `syncPromoterSwitch()` → `setData(false)` → 入口消失

中间这个窗口就是截图机会（审核是录屏的，逐帧回看必然抓到）。

更糟的是 `syncPromoterSwitch()` 第一行：
```js
if (m.promoterEnabled === undefined || m.promoterEnabled === null) return
```
`bootMerchant` 失败（超时/断网）时 `globalData.merchant` 压根没这个字段
→ 直接 return → 入口**永久停留在显示状态**。

### bug 2：入口藏了，但页面本身能直达

`app.json` 里 4 个 promoter 页面都注册着，可以直接跳
`pages/promoter/withdraw/index`。而该页 `onLoad` 先
`applyRule(FALLBACK_RULE)` 用**本地兜底常量**把规则渲染出来，
再去请求后端。后端 `DistributorAuthInterceptor` 确实返 403，
但那只影响数据 —— **页面骨架 + 那张写着「单笔最低 10 元」
「每日 3 次」「9:00-21:00」的提现规则卡片是本地常量渲染的，照样完整显示**。

这正好对应驳回里说的「设置提现门槛」。后端注释其实预言过这个坑
（「前端隐藏入口只是体验层，服务端必须自己挡」）—— 服务端挡住了
**数据**，但没挡住**页面渲染门槛文案**。

## 恢复步骤（过审后）

### 1. 前端复原（4 个文件，见上表）

用 git 最省事 —— 本次摘除是单个 commit，直接反向 apply：
```bash
git log --oneline --all --grep="摘除推客" | head -3
git revert <那个 commit>            # 或
git show <那个 commit> | git apply -R
```

### 2. 恢复前先解决"门槛"问题，否则还会被驳回

⚠️ **这是关键**：本次只是把功能藏起来过审，**驳回意见本身没有解决**。
直接恢复推客功能重新提交，会撞上同一个驳回。恢复前必须先处理：

审核员卡在四道门槛上（`sys_config` 的 `withdraw.*`，改值不用改代码）：

| 配置 key | 当前值 | 建议 | 理由 |
|---|---|---|---|
| `withdraw.minAmount` | 10 | **0.3** | 测试号佣金常只有几分几毛，10 元起提直接被拦，判定「无法成功提现」。0.3 是微信零钱转账渠道下限，属渠道约束不算平台门槛 |
| `withdraw.startHour` / `endHour` | 9 / 21 | **0 / 24** | 审核常在夜间进行，非受理时段直接被拦。代码里 `start==end` 或 0-24 即全天受理 |
| `withdraw.dailyTimes` | 3 | 10 或 0(不限) | 保留防刷但不构成门槛 |
| `withdraw.arrivalDesc` | 审核通过后 1-3 个工作日到账 | 见下 | — |

**还有一条硬伤**：驳回里「无法**即时**提现」指的是当前流程是
**人工审核 + 1-3 工作日**。审核员提交完只看到「待审核」，钱没到账。
这在微信眼里属于提现服务不完整。三条路：

- **A. 接入微信「商家转账到零钱」**（真·即时到账，微信认可的做法）
  审核通过后自动调 `transfer_bill` 打款，秒到零钱。
  代价：要开通微信支付「商家转账」产品权限（需商户号资质、可能单独申请）、
  写转账接口 + 回调 + 失败重试。**依赖商户号能否开通这个外部条件**。
- **B. 保留人工审核，压时效 + 加自动审核开关**
  提现页明确写「提交后 24 小时内完成审核」，小额自动放行。
  成本低但仍有二次驳回风险。
- **C.（本次选的）暂时摘除，过审后再说**

建议恢复时走 **A**，那是唯一能彻底消掉「即时」这个质疑的方案。

### 3. 恢复后必须验证的点

```bash
bash .github/scripts/smoke-promoter-removed.sh   # 恢复后这个脚本应该整体失败/删除
```
恢复推客后，把 `smoke-promoter-removed.sh` 改成反向断言（入口应渲染、
页面应可达），或直接删掉换成 `smoke-promoter-switch.sh`（已存在，27 项）。

另外 bug 1 的根因（默认 `true` + 失败时永久显示）**恢复时别原样退回**：
`promoterEnabled` 应保持默认 `false`，`syncPromoterSwitch` 拿不到值时
也应当按"不显示"处理。原来的取向（宁可多显示）在过审这件事上是反的。
