# 预约模型：后台各字段到底管什么

回答「后台的预约服务是不是可以不要、预约日期和预约时间是不是用来限制小程序可选的预约日期和时间的」。

结论先说：**不是**。后台「预约管理」里的预约日期/预约时段是**某一个已存在场次自己的属性**，
不是「可约范围」的配置项。小程序上顾客能选哪天、能选哪个点，跟这三个字段完全无关。

## 一、预约是「场次 + 报名」两张表

| 表 | 一行代表 | 谁产生 |
|---|---|---|
| `biz_booking` | 一个**场次**：某门店 + 某天 + 某时段 | 顾客提交时自动建，或后台手工建 |
| `biz_booking_member` | 一条**报名**：谁、几个人、联系方式 | 顾客提交 |

一个场次可以有多人报名。顾客提交时（`POST /api/booking`）：
同门店 + 同日期 + 同时段 + 同预约类型的场次已存在就复用，不存在才新建。

所以后台看到的每一行 `biz_booking`，都是「已经有人约了这个点」或者「运营手工开了这个点」，
**它是结果，不是规则**。

## 二、小程序可选日期/时段实际由什么决定

代码在 `BookingServiceImpl.selectAvailableSlots()`：

| 顾客端看到的 | 来源 | 在哪配 |
|---|---|---|
| 可选日期 | **门店 `booking_ahead_days`**（默认 7） | 门店管理 → 可提前预约 |
| 可选时段的起止 | **门店 `business_hours`** | 门店管理 → 营业时间 |
| 时段粒度（几分钟一档） | **门店 `booking_slot_minutes`**（默认 60=整点） | 门店管理 → 时段粒度 |
| 歇业日（每周几不可约） | **门店 `booking_closed_days`** | 门店管理 → 每周歇业日 |
| 单时段可约人数 | `sys_config` 的时段容量参数 | 参数设置 |
| 某时段「已约满」 | 该场次已报名人数 ≥ 容量 | 自动算 |
| 某时段「已过时」 | 当天且小时数 ≤ 当前小时 | 自动算 |

举例：门店营业时间填 `09:00-18:00` → 顾客看到 09:00~17:00 共 9 个整点。
改成 `10:00-22:00` → 顾客看到 10:00~21:00。
**要调整顾客可选时段，改的是门店营业时间，不是预约管理里的时段字段。**

跨天营业（如 `18:00-02:00`）按营业到 24 点处理；营业时间没填或格式不认时默认 10-22。

## 三、那后台这几个字段有什么用

- **预约服务（`product_id`）/ 服务名称（`service_name`）**：标记这个场次卖的是什么。
  顾客端提交时 `service_name` 现在跟着预约类型走（原先前端写死「堂食预约」，
  后台配了「到店消费」也会被存成堂食，已修）。
  **不建议删**：后台手工开场次、以及按服务筛选历史预约都要用它。
- **预约日期 / 预约时段**：这个场次是哪天哪个点。手工建场次时必填。
- **预约类型（`booking_type`）**：走 `sys_dict_data` 的 `biz_booking_type` 字典
  （堂食预约 / 到店消费 / 其他预约，商家可在「字典管理」自行增删）。
  小程序预约首页现在按这个字典渲染卡片，配几条显示几张。

## 四、限制「可约范围」——已实装（v10）

原先这一节写的是「现在没有这个能力，建议加在门店级」。**已经做了**，
见 `sql/upgrade/biz_store_booking_rule_v10.sql`，三个字段都加在 `biz_store` 上
（不动 `biz_booking` 的场次语义 —— 一行既是规则又是已发生的场次，后台列表就没法看了）：

| 字段 | 后台位置 | 含义 | 默认 |
|---|---|---|---|
| `booking_ahead_days` | 门店管理 → 可提前预约 | 能约未来几天（含今天），1~60 | 7 |
| `booking_slot_minutes` | 门店管理 → 时段粒度 | 15 / 30 / 60 / 120 分钟一档 | 60（整点） |
| `booking_closed_days` | 门店管理 → 每周歇业日 | 1-7 逗号分隔（1=周一，7=周日），空=每天可约 | 空 |

默认值刻意与改造前行为一致（7 天 / 整点 / 不歇业），已有门店升级后表现不变。

### 接口

- `GET /api/booking/days?storeId=` 新增。返回 `aheadDays / slotMinutes / closedDays /
  openCount / days[{date,label,weekday,weekdayText,closed,closedReason}]`。
  小程序预约页原先写死 `getNextDays(7)`，现在改调这个接口。
- `GET /api/booking/slots?storeId=&date=` 增加 `slotMinutes / closedDay / outOfRange /
  closedReason`，每个时段多返回一个 `closed`。
  歇业日/越界日期**仍然把时段列出来**并全部标 `closed` —— 返回空数组的话前端只能显示
  「暂无时段」，用户分不清是歇业还是门店没配营业时间。

### 边界（都有单测/smoke 护着）

- 天数填 0 / 负数 / null → 回退 7；填 999 → 夹到 60。
- 粒度填 0 / 负数 / 45 这类非枚举值 → 回退 60。
  **这条最关键**：粒度是 `minutes += stepMinutes` 的步长，取 0 会死循环把线程占满。
- 歇业日用 ISO 的 1=周一，而 `Calendar.DAY_OF_WEEK` 是 1=周日，
  换算错一位就会把周日的配置作用到周六 —— `BookingRuleTest` 对 7×7 组合全遍历。
- 存量脏数据（例如后台历史上存了「周一」）忽略该项，不让整个预约页 500。
- 过去的日期一律拦掉，否则顾客改一下 `date` 参数就能约到昨天。

验证入口：`.github/scripts/smoke-booking-rule.sh`（15 断言，改真实门店配置断言接口输出跟着变，跑完复原）
+ `BookingRuleTest`（6 个纯逻辑单测，无库也能跑）。

## 五、还没做的

- 「不可约的具体日期」（春节这种单次歇业，不是每周固定）—— 现在只能按星期配。
- 时段级容量差异（午市 20 人、晚市 10 人）—— 现在 `slotLimit` 是全门店一个值。
