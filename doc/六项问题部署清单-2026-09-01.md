# 六项问题：为什么改好了线上还看不到，以及怎么一次性部署到位

对应用户反复报的六项：

1. 首页门店评分没有
2. 首页基础设施（服务设施标签）没有
3. 「联系商家」的拨打电话没有；「在线咨询」里客服电话和客服二维码没有
4. 预约首页「堂食预约」写死了，应该来自后台
5. 支付时拿到的手机号带星号
6. 后台的「预约服务」是不是可以不要；预约日期/时间是不是用来限制小程序可选范围的

## 结论：六项代码侧都已完成，卡的是部署

本地实测 `verify-prod-6items.sh` → **PASS=12 FAIL=0**（唯一 ⚠️ 是门店 rating 没填）。
生产实测同一脚本 → **FAIL=3**，三条全部指向「线上跑的还是旧包」：

| 生产实测 | 说明 |
|---|---|
| ❌ `/api/booking/types` 返 code=401 | 旧 jar 里 `/api/booking/**` 整体要登录，没有这个匿名端点 → 第 4 项无从生效 |
| ❌ `/api/merchant/info` 缺 `phone` | 第 3 项「拨打电话」的商家兜底字段 → 旧 jar 没返 |
| ❌ 后台 dist 是旧包 | **本轮新查出来的**，见下 |

## 本轮新查出来的真因：后台前端也是旧包

第 1 项「门店评分」之前一直被归因为「后台没填数据」。这一轮把生产的 admin
产物拆开看了，结论要更正：**用户根本没地方填**。

定位方法（`/admin/index.html` 内联 webpack runtime 里有 chunk→hash 映射，
`app.*.js` 里有路由→chunk 映射，两者拼出门店页真实文件名）：

```
生产门店管理页 chunk = /admin/static/js/chunk-0a494b61.d230f08b.js  (25KB)
  门店评分     MISS
  可提前预约   MISS
  时段粒度     MISS
  每周歇业日   MISS
  客服服务时间 HIT      ← 说明这个包比更早的版本新，但仍早于 v8/v10
```

也就是说：`rating` 列（v8）和三个预约规则列（v10）后端有、SQL 有、源码表单有，
但线上后台的门店编辑弹窗里这四个表单项都不存在。所以第 1 项不是「忘了填」，
是「填不了」；第 6 项的「可提前预约 / 时段粒度 / 每周歇业日」同理也配不了。

顺带说明：**本地 `ruoyi-ui/dist` 当时也是 8-31 的旧包**（`门店评分` 只在一个
过期 chunk 里、`每周歇业日` 完全没有）。已重新 `npm run build:prod`，
新包 `chunk-5aaec418.0be26b17.js` 四项全部 HIT。

这个坑已经加进 `verify-prod-6items.sh` 的【前置】段，以后 jar 和 dist
任一没更新都会报红，不会再误判成「数据没填」。

## 部署步骤

三样东西要一起上，缺一个就会出现「部分生效」：

### 1) 先跑 SQL（幂等，可重复执行）

```bash
mysql --default-character-set=utf8mb4 -h<RDS> -urds_root -p bx_wetuangou \
  < sql/upgrade/biz_store_rating_booking_type_v8.sql      # 第 1、4 项：rating 列 + 预约类型字典
mysql --default-character-set=utf8mb4 -h<RDS> -urds_root -p bx_wetuangou \
  < sql/upgrade/biz_store_booking_rule_v10.sql            # 第 6 项：可提前预约/时段粒度/歇业日
```

两个脚本都已接入 `sql/deploy/init-all.sh`（第 127、129 行），
新库直接跑 init-all 即可，老库按上面单独补。

### 2) 传 jar + dist.zip，一条命令切换

本地产物（都已验证含本轮改动）：

```
ruoyi-admin/target/ruoyi-admin.jar        含 assertSlotBookable、含新的小程序模板
ruoyi-ui/dist.zip                         含 门店评分/可提前预约/时段粒度/每周歇业日
```

```bash
scp ruoyi-admin/target/ruoyi-admin.jar root@daodian:/data/wwwroot/daodian/
scp ruoyi-ui/dist.zip                  root@daodian:/data/wwwroot/daodian/
ssh root@daodian '/data/wwwroot/daodian/start.sh all'   # 换前端 + 重启后端
```

`start.sh all` 会先原子切换 `www/admin`（先落 admin.new 再改名，避免
`mv` 到已存在目录变成 `www/admin/dist/` 那种只表现为白屏的静默失败），
再停旧起新并等健康检查通过。

### 3) 重新上传小程序

第 3 / 4 / 5 项以及本轮的券入口、预约日期改动都在小程序侧。
`miniprogram7/` 是唯一源，后台「一键打包」读的模板已由构建期自动同步
（`lint-mp-template.sh` 守着这点）。

### 4) 部署后跑验收

```bash
BASE=https://daodian.lanaoboxiang.com APPID=wx7d1c43cb9a27abc7 \
  bash .github/scripts/verify-prod-6items.sh
```

期望：前置三条全绿。此时再去后台【门店管理】编辑门店：

- 填「门店评分」（0.1~5.0）→ 第 1 项出现
  **别填 0** —— 0 会被当成真实差评展示，不是「未评分」
- 需要限制预约范围时填「可提前预约 / 时段粒度 / 每周歇业日」→ 第 6 项

## 第 6 项的直接回答

**后台「预约服务」不建议删**，但它不是你以为的那个东西：

- `biz_booking` 每一行是一个**已存在的场次**（某门店 + 某天 + 某时段），
  是**结果不是规则**。后台手工开场次、按服务筛历史预约都要用它。
- 顾客能选哪天哪个点，与 `biz_booking` 里任何一行无关。实测把门店
  `business_hours` 从 `10:00-22:00` 改成 `14:00-19:00`，小程序可选时段
  立刻从 `[10..21]` 变成 `[14..18]`；而库里那些 15:00 的历史场次毫无影响。
- 真正的「可约范围」配置项在**门店级**（v10 新增）：可提前预约天数 /
  时段粒度 / 每周歇业日。详见 `doc/预约模型说明-后台字段职责-2026-09-01.md`。

另外这一轮发现可约范围**只在小程序端拦**：日期条置灰、时段标 closed，
但直接 POST `/api/booking` 时后端一行校验都没有 —— 歇业日、超出可提前天数、
已过去的日期、营业时间外的 03:00、甚至 `timeSlot:"随便填"` 全部 200 落库。
已补 `assertSlotBookable`，并由 `smoke-booking-submit-guard.sh` 锁住（17 断言）。
