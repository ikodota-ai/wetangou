```ini
# /etc/systemd/system/dytuangou.service

Description=洞天团购后端
After=network.target

[Service]
Type=simple
User=dytuangou
Group=dytuangou
WorkingDirectory=/var/dytuangou/app
EnvironmentFile=/etc/dytuangou/dytuangou.env
ExecStart=/opt/jdk17/bin/java \
  -Xms512m -Xmx1024m \
  -Dfile.encoding=UTF-8 \
  -jar /var/dytuangou/app/ruoyi-admin.jar \
  --spring.profiles.active=prod \
  --server.port=8083 \
  --server.forward-headers-strategy=native \
  --ruoyi.storage.s3.public-domain=https://wetuango.oss-cn-shenzhen.aliyuncs.com
Restart=always
RestartSec=10
StandardOutput=append:/var/dytuangou/logs/stdout.log
StandardError=append:/var/dytuangou/logs/stderr.log

[Install]
WantedBy=multi-user.target
```

三个容易漏、且漏了会直接出故障的参数：

- `--server.forward-headers-strategy=native`
  Spring Boot 默认是 `NONE`，即**不信任** Nginx 传来的 `X-Forwarded-Proto`。
  不加这条，Tomcat 认为自己在跑 http，`ServerConfig.getUrl()`（基于
  `request.getRequestURL()`）就会生成 `http://...` 的地址 ——
  商户「微信配置」里点「自动生成」得到的支付回调地址是 http，
  而微信支付只接受 https 回调，最终表现为回调静默不到账。
- `--ruoyi.storage.s3.public-domain=...`
  不配时 `S3StorageAdapter.getPublicUrl()` 会拼 path 风格
  `endpoint/bucket/key`，阿里云 OSS 不支持这种形式，图片链接打不开。
  必须显式给 virtual-hosted 风格域名（`https://<bucket>.<endpoint host>`）。
- `--server.port=8083`
  与 Nginx 的 `proxy_pass` 保持一致；同时确认安全组/防火墙**不要**放通 8083，
  公网只经 443 进来。

```bash
systemctl daemon-reload
systemctl enable dytuangou
systemctl start dytuangou
systemctl status dytuangou    # 看是否 active (running)
journalctl -u dytuangou -f    # 跟日志
```

## 6. Nginx 反向代理 + HTTPS

管理端 dist 与 API 同域部署：`/` 走静态文件，`/prod-api/` 和 `/api/` 反代到后端。

```nginx
# /etc/nginx/conf.d/daodian.lanaoboxiang.com.conf

# 80 端口只做跳转，不要再指向任何站点根目录。
# 常见坑：面板默认站点（如 OneinStack）会占着 80，
# 结果 https 已经是新版前端、http 还返回几年前的默认欢迎页。
server {
    listen 80;
    server_name daodian.lanaoboxiang.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    http2 on;
    server_name daodian.lanaoboxiang.com;

    ssl_certificate     /etc/letsencrypt/live/daodian.lanaoboxiang.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/daodian.lanaoboxiang.com/privkey.pem;
    ssl_session_timeout 1d;
    ssl_session_cache shared:SSL:50m;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    # 上传私钥/图片，20M 够用；小于文件大小会返回 413
    client_max_body_size 20M;

    # 下面三个 location 都必须传 X-Forwarded-Proto，
    # 且后端要配 server.forward-headers-strategy=native 才会采信（见 §5）。

    # web root 只到 www/ 这一层。
    #
    # 千万别指向 /data/wwwroot/daodian —— 那个目录里有 ruoyi-admin.jar、
    # cert/（微信支付私钥）、logs/，指过去等于全部开放下载。
    # 实测确认过：现在 curl /ruoyi-admin.jar、/cert/apiclient_key.pem 返回的是
    # 兜底首页而不是文件本体，说明 root 在 web 目录层，是对的。
    #
    # /data/wwwroot/daodian/
    # ├── ruoyi-admin.jar / cert/ / logs/ / uploadPath/   ← root 之外
    # └── www/                                            ← root 就是这里
    #     ├── index.html          系统介绍页（静态单文件，含后台入口+小程序码）
    #     ├── xc8sanE9NO.txt      域名校验文件（放这层，重传后台不会被删）
    #     └── admin/              后台 dist 全部内容
    root /data/wwwroot/daodian/www;
    index index.html;

    # 域名/小程序校验文件：独立目录，覆盖 dist 时不会被删。
    # location = /robots.txt 必须排在前面 —— 正则 location 优先级高于前缀 location，
    # 不放行的话 /robots.txt 会被下面的 .txt 正则抢走、去 verify/ 里找、404（实测过）。
    location = /robots.txt { }

    location ~ ^/(MP_verify_\w+|[A-Za-z0-9]+)\.txt$ {
        root /data/wwwroot/daodian/verify;
        default_type text/plain;
        access_log off;
    }

    # 两个 SPA 入口都要 no-cache。
    # 迁到 /admin/ 之后，原来的 `location = /index.html` 命中的是**介绍页**，
    # 后台入口 /admin/index.html 反而没了 no-cache —— 换版时用户会拿到旧 HTML
    # 配新 hash 的资源文件，表现为白屏。所以这里两个入口一起盖住。
    # 实测：/admin/system/user 也会命中（try_files 内部跳转会重新匹配 location）。
    location ~ ^/(index\.html|admin/index\.html)$ {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
    }

    # 后台带 hash 的静态资源可以长缓存。
    # 注意前缀是 /admin/static/ 不是 /static/ —— publicPath 改了之后
    # 原来的 `location /static/` 一条都命中不到，强缓存等于白配（实测过）。
    location /admin/static/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # 后台管理端：ruoyi-ui 打包时 publicPath=/admin/，资源引用是 /admin/static/**。
    # 必须有自己的 try_files 兜到 /admin/index.html —— 否则后台内页刷新
    # （如 /admin/system/user）会掉到下面 location / 的介绍页去。
    location /admin/ {
        try_files $uri $uri/ /admin/index.html;
    }

    # 站点根：系统介绍页。
    # 注意兜底给的是介绍页的 index.html，不再是后台 SPA 的入口。
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 管理端 API 前缀：ruoyi-ui/.env.production 里 VUE_APP_BASE_API=/prod-api
    location /prod-api/ {
        proxy_pass         http://127.0.0.1:8083/;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_http_version 1.1;
        proxy_read_timeout 60s;
    }

    # 小程序 / 微信支付回调走 /api/**（SecurityConfig 里对 /api/** 是 permitAll）
    location /api/ {
        proxy_pass         http://127.0.0.1:8083/api/;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_http_version 1.1;
        proxy_read_timeout 60s;
    }

    # 本地上传文件的静态映射（ResourcesConfig 把 /profile/** 映射到 ruoyi.profile）
    location /profile/ {
        proxy_pass       http://127.0.0.1:8083/profile/;
        proxy_set_header Host $host;
    }
}
```

### 6.1 目录结构与首次迁移（后台从 `/` 挪到 `/admin/`）

站点根路径 `/` 现在是**系统介绍页**（一个手写的静态 HTML，仓库里在 `site/index.html`），
后台管理端整体挪到 `/admin/`。

**为什么要加 `www/` 这一层**：nginx 的 `root` 必须落在一个只有 web 资源的目录上。
原来 root 是 `/data/wwwroot/daodian/dist`，现在既要放介绍页又要放后台，
如果直接把 root 上移到 `/data/wwwroot/daodian`，那么 `ruoyi-admin.jar`、
`cert/`（微信支付私钥）、`logs/`、以及**含 RDS 密码和 OSS AK/SK 的 `start.sh`**
就全部可以被公网直接下载。所以新建 `www/`，敏感文件留在它外面。

**为什么不让 `www` 和 `admin` 平级**（用 `alias` 各指一个目录）：
纯粹是为了少一层配置——`root` 一行就能覆盖两者，不需要给 `/admin/` 单独写 `alias`。
（早先本文写过"alias + try_files 会二次解析成 `admin/admin/index.html` 而 404"，
已在 nginx 1.26.2 实测**否定**：`/admin/aaa/bbb` 正常兜到后台 SPA，error log 无此痕迹。
平级方案技术上可行，只是配置更啰嗦，且敏感文件仍需单独确认在 root 之外。）

```
/data/wwwroot/daodian/
├── ruoyi-admin.jar        ← 以下都在 web root 之外，公网访问不到
├── start.sh               ← 含 RDS 密码 / OSS AK-SK，绝对不能进 root
├── cert/                  ← 微信支付私钥
├── logs/  uploadPath/
└── www/                   ← nginx root
    ├── index.html         介绍页（= 仓库 site/index.html，手工上传，不参与前端构建）
    ├── miniprogram-qr.png 小程序码（介绍页引用）
    ├── xc8sanE9NO.txt     域名校验文件（放这层，重传后台不会被删）
    └── admin/             后台 dist 的全部内容
```

介绍页是**纯静态单文件**，不从 `dist.zip` 解压，也不需要构建 —— 改文案直接编辑
`site/index.html` 上传覆盖即可。

首次迁移：

```bash
cd /data/wwwroot/daodian
mkdir -p www
mv dist www/admin                  # 把现有后台整体挪进去（不用重新解压）
# 上传：site/index.html → www/index.html
# 上传：小程序码 → www/miniprogram-qr.png
mv verify/*.txt www/ 2>/dev/null   # 域名校验文件挪到 root 内，见下方说明
chown -R www:www www
nginx -t && systemctl reload nginx
```

之后每次换后台版本：

```bash
cd /data/wwwroot/daodian
unzip -o dist.zip -d /tmp/newdist
rm -rf www/admin && mkdir -p www/admin
mv /tmp/newdist/dist/* www/admin/
chown -R www:www www/admin
```

**域名校验 `.txt`**：用独立目录 `/data/wwwroot/daodian/verify/` + 专属 `location`，
这样每次覆盖后台 dist 都不会把校验文件删掉。该 location 自带 `root`，
所以 `verify/` 放在主 root 之外**没有问题**：

```nginx
    # 排在 .txt 正则之前：正则 location 优先级高于前缀 location，
    # 不单独放行的话 /robots.txt 会被下面那条规则抢走并 404（实测过）。
    location = /robots.txt { }

    location ~ ^/(MP_verify_\w+|[A-Za-z0-9]+)\.txt$ {
        root /data/wwwroot/daodian/verify;
        default_type text/plain;
        access_log off;
    }
```

（早先本文推断"因为 `verify/` 在 root 之外所以 nginx 读不到"，**是错的** ——
该 location 有自己的 `root`，与主 root 无关。真实原因是当时正则写成
`[A-Za-z0-9]{16,}`，而 `xc8sanE9NO` 只有 10 个字符，长度不够匹配不上。
放宽成 `[A-Za-z0-9]+` 后已实测可用。）

**三处必须同时一致**，改一个就得改另两个，否则表现为「页面白屏 + 控制台一堆 404」：

| 位置 | 值 | 作用 |
|---|---|---|
| `ruoyi-ui/vue.config.js` `publicPath` | `/admin/` | 决定 dist 里静态资源的引用前缀 |
| `ruoyi-ui/src/router/index.js` `base` | `process.env.BASE_URL`（由 publicPath 注入） | history 模式下如何从 URL 解析路由 |
| nginx `location /admin/` | `try_files $uri $uri/ /admin/index.html` | 内页刷新兜底，缺了会掉到介绍页 |

另外有三处**写死根路径**的跳转已一并改成 `process.env.BASE_URL + 'index'` /
`<%= BASE_URL %>`：`layout/components/Navbar.vue`（注销）、`utils/request.js`
（401 重新登录）、`public/index.html`（IE 提示页）。不改的话点注销会跳到介绍页。

API 前缀不受影响：`.env.production` 里 `VUE_APP_BASE_API='/prod-api'` 是绝对路径，
与 `publicPath` 解耦。

**三种身份的落地路径**（登录后由 `login.vue` 的 `resolveEntryPath()` 按后端返回的
`userType` 分流，加上 `/admin/` 前缀后是）：

| 身份 | userType | 登录后落地 |
|---|---|---|
| 平台 | `0` | `/admin/index` |
| 代理商 | `1` | `/admin/agent/index` |
| 商户 | `2` | `/admin/merchant/index` |

**为什么不给三种身份各开一个入口路径**（如 `/平台/`、`/商户/`）：身份来自后端，
登录接口的请求体只有账号密码，`userType` 是登录成功后 `getInfo` 才返回的 ——
入口 URL 在用户输账号之前就已确定，那时系统还不知道他是谁。硬做的话要么打三份
dist（每份一个 `publicPath`），要么让三个前缀共用一份，但 `router base` 只能配一个值，
另两个前缀下路由会全部失配（撞上 `store/modules/permission.js` 里的 `path:'*'`
兜底，跳 `/404` 且 URL 掉出前缀）。

需要给不同身份发专属链接时，用 query 参数即可（只切登录页的 tab 与提示文案，
**不参与鉴权**，真实身份仍由后端决定）：

```
https://daodian.lanaoboxiang.com/admin/login?entry=merchant
https://daodian.lanaoboxiang.com/admin/login?entry=agent
https://daodian.lanaoboxiang.com/admin/login?entry=platform
```

非法值（含 `__proto__`、`constructor` 这类原型链上的键）一律回落到「平台」tab。

### 6.2 验证 HTTPS 与协议透传

```bash
# 证书有效 + 首页是新版前端
curl -sS -o /dev/null -w "code=%{http_code} ssl=%{ssl_verify_result}\n" \
  https://daodian.lanaoboxiang.com/

# http 必须 301 到 https（返回 200 说明 80 还挂着别的站点根）
curl -sS -o /dev/null -w "code=%{http_code}\n" http://daodian.lanaoboxiang.com/

# 两个 API 前缀都要通
curl -sS https://daodian.lanaoboxiang.com/api/ping          # {"msg":"pong","code":200}
curl -sS -o /dev/null -w "%{http_code}\n" https://daodian.lanaoboxiang.com/prod-api/captchaImage
```

### 6.4 支付私钥为什么放在上传目录之外

`ResourcesConfig` 把 `/profile/**` 整个映射到 `ruoyi.profile` 目录，
而 `SecurityConfig` 对 `/profile/**` 是 `permitAll`。
若把 `apiclient_key.pem` 存在 `ruoyi.profile` 里面，任何人都能用
`/profile/cert/merchant_1_apiclient_key.pem` 直接下载走商户私钥。

因此 `BizMerchantCertController` 落盘到 `ruoyi.profile` 的**同级** `cert/`
（目录 700 / 文件 600），不在任何静态映射范围内。
备份服务器时注意这个目录**不要**打进对外可下载的包。

### 7.1.1 升级后必查的三类脏数据

新版本对租户归属做了收严，上线前用下面三条 SQL 体检，**有结果就必须先补数据**。

```sql
-- ① 商户账号没绑 merchant_id
SELECT user_id, user_type, agent_id, merchant_id FROM biz_merchant_user
WHERE user_type = '2' AND (merchant_id IS NULL OR merchant_id = 0);
```

旧版本这种账号会被**静默兜底成商户 1**，等于能读写商户 1 的全部数据且没有任何
告警。新版本改为降级到无权限（内部 merchant_id 记 -1）：列表查不到数据、增删改
一律 403，日志会打 ERROR 带 userId。所以查出来的账号上线后会「突然用不了」，
必须提前把 merchant_id 补对。

> 为什么不是直接置 null：租户过滤是 `<if test="merchantId != null">`，
> null 会导致 where 条件整个不拼接 → 反而看到全平台数据，比兜底成商户 1 更糟。
> 所以用 -1 这个不存在的哨兵值，让它必然命中空集。

```sql
-- ② 不属于任何商户的孤儿商品
SELECT product_id, product_name, status FROM biz_product
WHERE merchant_id = 0 OR merchant_id IS NULL;
```

小程序按 merchantId 过滤商品，这些商品的症状是「后台建出来了但用户看不到」。
确认归属后归位：`UPDATE biz_product SET merchant_id = 1 WHERE product_id IN (...);`

这类商品点上架会被拦下并提示「该商品未归属任何商家，无法上架」。
注意早期版本这里报的是「门店 X 不属于该商家」—— 因为归属为 0 时会一路走到
门店归属校验，而用户看到的门店明明是自己的，很难联想到真正缺的是商品归属。

```sql
-- ②b 跨商家商品：商品归属与它的适用门店归属不一致
SELECT p.product_id, p.product_name, p.merchant_id AS prod_mch,
       s.store_id, s.merchant_id AS store_mch, s.store_name
FROM biz_product p JOIN biz_store s ON FIND_IN_SET(s.store_id, p.store_ids)
WHERE p.merchant_id <> s.merchant_id;
```

新版本禁止商品挂到别家商户的门店上，所以查出来的商品**保存和上架都会失败**。
要么把商品的 merchant_id 改成门店所属商户，要么把适用门店换成本商户自己的门店。

```sql
-- ③ 角色 id 是否与开发库一致（整表替换过 sys_menu/sys_role_menu 时尤其要查）
SELECT role_id, role_key, role_name FROM sys_role ORDER BY role_id;
```

开发库为 1 admin / 2 common / 3 platform / 4 agent / 5 merchant。
若生产的 role_id 与此不同，直接导入 `sys_role_menu` 会把菜单绑到错误的角色上。

### 7.2 改完菜单后要处理的缓存（不是 flushdb）

**菜单本身没有缓存。** `SysMenuServiceImpl` 里不存在任何 redisCache/@Cacheable，
`SysLoginController.getRouters()` 每次都实时 `selectMenuTreeByUserId` 查库。
改完 `sys_menu` 刷新页面就能看到新菜单。

> 本文档 v1.0.2 之前写的"改完菜单必须 `redis-cli -n 0 flushdb`"是**错的**：
> 既没必要（菜单不走缓存），又危险（生产 Redis 与其它业务共用 db，见 §7.3）。

真正会滞后的是**权限集合** `LoginUser.permissions`，它随登录态一起存在
`login_tokens:<uuid>` 里（`TokenService`）。所以改完 `sys_role_menu` 后：

```bash
# 首选：让受影响的账号退出重登；或后台「系统监控 → 在线用户」强制退出
# 需要手工清时，只删登录态这一个前缀，不要动其它 key
redis-cli -n 3 --scan --pattern 'login_tokens:*' | xargs -r -n 200 redis-cli -n 3 del
```

其余缓存的正确清理入口：

| 缓存 | 前缀 | 清理方式 |
|---|---|---|
| 登录态/权限 | `login_tokens:` | 重新登录 / 在线用户强退 |
| 参数配置 | `sys_config:` | 后台「参数设置」→ 刷新缓存 |
| 数据字典 | `sys_dict:` | 后台「字典管理」→ 刷新缓存 |
| 商户（含 appid） | `merchant:id:` `merchant:appid:` | 改商户时 `MerchantServiceImpl` 自动清 |
| 后台账号租户归属 | `merchant:user:` | **无自动清理**，改了账号 merchant_id 需手工删 |
| 小程序会员态 | `member_tokens:` | 带 TTL，自动过期 |
| 微信各类 token | `wx:miniapp:*` `wx:open:*` | 带 TTL，自动过期 |
| 验证码/防重/限流/密码错误数 | `captcha_codes:` `repeat_submit:` `rate_limit:` `pwd_err_cnt:` | 带 TTL，自动过期 |

后台「系统监控 → 缓存列表」只登记了 `CacheConstants` 里的 7 个前缀，
`merchant:*` / `member_tokens:` / `wx:*` 在页面上看不到，只能用 `redis-cli`。

> ⚠️ 该页面右上「清理全部」走的是 `redisTemplate.keys("*")` + `delete`，
> 等价于 `flushdb`。**只有在按 §7.3 换到独立 db 之后才可以点**。

### 7.3 Redis 独占一个 db（生产必做）

生产 Redis 是本机实例且与其它业务共用，若本应用也落在 `db0`，
则「清理全部」按钮和任何 `flushdb` 都会连带删掉别人的 key。

选一个空闲 db：

```bash
redis-cli -n 0 config get databases   # 默认 16，即 0-15
redis-cli info keyspace               # 已有 key 的 db 会列出 dbN:keys=...
```

启动参数指定（**必须是 `spring.data.redis.database`**；
Boot 4 不认旧的 `spring.redis.*`，写错会静默回落到 db0）：

```
--spring.data.redis.database=3
```

验证：

```bash
# 重启后登录一次后台
redis-cli -n 3 dbsize
redis-cli -n 3 --scan --pattern 'login_tokens:*' | head
```

切换的两个副作用：

1. 旧 db 里的登录态不再被读取 → **所有后台和小程序用户需重新登录**，选低峰期切。
2. 旧 db0 里 `sys_config:` / `sys_dict:` / `merchant:*` 是**无 TTL** 的，
   不会自己消失，切换后手工清一次残留：

```bash
for pattern in 'sys_config:*' 'sys_dict:*' 'merchant:id:*' 'merchant:appid:*' 'merchant:user:*'; do
  redis-cli -n 0 --scan --pattern "$pattern" | xargs -r -n 200 redis-cli -n 0 del
done
```

> 一律用 `--scan` 而不是 `keys`：`keys` 会阻塞 Redis 主线程，
> 在共用实例上会拖慢其它业务。

> 分配新的 `menu_id` 前**务必先查占用**：
> `select menu_id, menu_name from sys_menu where menu_id between 2290 and 2300;`
> 曾经因为直接用了"看起来空着"的 2292/2293，把商品菜单的权限误绑到平台角色上。

## 13. 第三方平台代发布（高级）

如需"一个平台账号管多商户、避免每个商户人工发布"，需要：

1. **注册微信第三方平台**（mp.weixin.qq.com → 第三方平台）
2. **全网发布**（500 元审核费，每年 300 元年审）
3. **授权流程**：
   - 商户扫码授权给第三方平台
   - 平台用 `authorizer_access_token` 代调微信接口
   - `POST /wxa/commit` 提交代码
   - `POST /wxa/submitaudit` 提交审核
4. **本项目已有的部分**（`WxOpenService` + `MpReleaseServiceImpl`）：
   - `component_access_token` / `authorizer_access_token` 拉取与 Redis 缓存 ✅
   - `submitAudit` / `release` / `revertRelease` 已接 ✅
   - 授权回调 `MpOpenCallbackController` 存 `refresh_token` ✅
   - `refresh_token` 轮换后自动落库 ✅（commit `2794c5ca` 修复，此前只打日志不落库，
     旧值失效后提审/发布会 401）
5. **仍缺的部分**（接入前必须补齐）：
   - **`/wxa/commit` 未接入**：微信侧顺序是 commit（上传代码）→ submitaudit → release，
     缺 commit 直接提审会报「无待审核版本」。`WxOpenService.commit()` 实现已就绪，
     只是没有调用方。
   - **`getAuthorizerInfo` 未接入**：授权成功后没回填小程序昵称/主体名，
     现在「小程序授权」列表里这些字段靠人工录入。
   - `WxOpenService.buildExtJson(Long,String,String)` 已标 `@Deprecated`，**不要用**：
     它缺 `extAppid`/`extEnable` 外层（微信 `/wxa/commit` 不认），
     且域名键名写成 `apiBaseUrl` 而小程序端读的是 `ext.baseUrl`。
     正确实现是 `MpReleaseServiceImpl.buildExtJson(Merchant)`。

**工作量预估**：3-5 天（含测试）。**当前版本不内置**，单商户自助发布已可走通。
