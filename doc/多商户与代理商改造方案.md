# 多商户 + 代理商 改造方案

> 目标：平台 → 代理商 → 商户 → 门店 四层体系。一个商户仅一个小程序 appid、可有多个门店；
> 代理商向平台缴费后自行开通商户并向商户收费；平台后台支持小程序代上传/代提审/代发布。

## 1. 层级与租户模型

```
平台(admin/platform)
 └─ 代理商 biz_agent            ← 向平台缴费换取「商户开通额度」
     └─ 商户 biz_merchant        ← 一商户一 appid，代理商在额度内开通并自行收费
         └─ 门店 biz_store       ← 一商户多门店
             └─ 商品/订单/会员/推客…
```

- **组织权限**用 `sys_dept` 三层（平台 → 代理商部门 → 商户部门），复用 RuoYi 自带部门数据权限管「账号/角色」可见范围。
- **业务隔离**用业务表上的 `merchant_id`，由租户上下文强制过滤，不依赖部门树，避免两套权限打架。
- `biz_merchant_user` 记录后台账号归属（0平台 / 1代理商 / 2商户），登录后据此构建租户上下文。

### 隔离级别约定

| 级别 | 说明 | 涉及表 |
| --- | --- | --- |
| 商户强隔离 | `merchant_id` 必须有值，跨商户不可见 | store、store_album、member、product、product_store、order、booking、booking_member、pay_bill、member_voucher、distributor、commission、withdraw、settle_account、settle_record |
| 平台级共享 | `merchant_id=0` 表示全平台通用，商户可另建自己的 | category、voucher、agreement、commission_rule |

> 查询平台级共享表时条件为 `merchant_id in (0, 当前商户)`。

### 唯一键变更（重要）

- `biz_member`：`uk_openid(openid)` → `uk_merchant_openid(merchant_id, openid)`。
  不同 appid 的 openid 属于不同命名空间，原全局唯一键会导致跨商户误判/冲突。
- `biz_distributor`：`uk_member(member_id)` → `uk_merchant_member(merchant_id, member_id)`，推客商户内独立。
- `biz_merchant.appid` 唯一索引，是小程序端反查商户的唯一入口。

## 2. SQL 脚本（已落库验证，幂等可重复执行）

按顺序执行：

```bash
mysql --default-character-set=utf8mb4 -uroot -p ry-vue < sql/biz_tenant_tables.sql   # 新建租户相关表
mysql --default-character-set=utf8mb4 -uroot -p ry-vue < sql/biz_tenant_upgrade.sql  # 存量表加 merchant_id + 回填 + 改唯一键
mysql --default-character-set=utf8mb4 -uroot -p ry-vue < sql/biz_tenant_menu.sql     # 租户管理菜单 + 三类角色
```

新增表：`biz_agent`、`biz_agent_fee`、`biz_merchant`、`biz_merchant_fee`、`biz_merchant_user`、`biz_mp_auth`、`biz_mp_release`。

存量数据处理：自动建「平台直营」代理商(id=1) 与「默认商户」(id=1)，
appid/支付凭证从 `sys_config` 现有全局配置迁移，全部存量业务数据回填 `merchant_id=1`，
`store_id=0` 的平台级记录保持 `merchant_id=0`。

### 3.2 自动过滤（已完成，避免手改 157 个文件）

用 MyBatis 拦截器统一给带 `merchant_id` 的表追加条件，无需逐个 Mapper XML 改 `<if>`：

```
ruoyi-framework/…/tenant/TenantSqlInterceptor.java    # 读侧：改写 select/update/delete
ruoyi-framework/…/tenant/TenantSqlRewriter.java       # SQL 改写核心
ruoyi-framework/…/tenant/TenantInsertInterceptor.java # 写侧：补齐/校验 merchantId
ruoyi-framework/…/tenant/TenantTableRegistry.java     # 强隔离表 / 平台共享表清单
ruoyi-framework/…/tenant/TenantIgnoreResolver.java    # @IgnoreTenant 判定（带缓存）
```

两个拦截器在 `MyBatisConfig` 通过 `sessionFactory.setPlugins(...)` 注册。

规则：
- 平台账号（userType=0）不加条件；
- 代理商账号（1）追加 `merchant_id in (该代理商名下商户)`；
- 商户账号（2）追加 `merchant_id = ?`；平台级共享表用 `merchant_id in (0, ?)`；
- `sys_*` 等非租户表不在注册表内自动跳过；`biz_agent*`/`biz_merchant*` 三个 Mapper 标 `@IgnoreTenant`
  （它们自身带 merchantId 字段，否则会被当业务数据误改）。
- update/delete 同样加租户条件，防止越权改删他人数据。

写入侧 `TenantInsertInterceptor`：商户账号**强制覆盖** `merchantId` 为自身（不信任客户端传值，
防伪造参数向他人租户写数据）；代理商账号未传商户则报错、传了必须是名下商户；平台账号不干预。

### 3.5 小程序端接口补租户维度（已完成）

`/api/**` 原本全是 `@Anonymous` 且无租户参数，多商户下会串数据。现改为由拦截器统一注入上下文，
业务 Controller 无需逐个改造：

- 已登录：从会员 token 载荷取 merchantId 写入上下文。
- 未登录（门店/商品列表等）：读请求头 `X-App-Id`（兼容 `appid` 参数）→ 查 `biz_merchant` → 写入上下文；
  取不到时兜底为默认商户 `TenantConstants.DEFAULT_MERCHANT_ID`，**不置空**，否则匿名接口会返回全平台数据。
- 小程序侧统一在 `miniprogram7/utils/request.js` 的请求头带上 `X-App-Id`，appid 配置在 `miniprogram7/utils/config.js`。

### 3.6 代理商开户额度校验（已完成）

`MerchantServiceImpl.insertMerchant` 中：代理商账号开通商户时校验代理商状态、
`expire_time` 未过期、`used_quota < merchant_quota`，成功后 `used_quota+1`；平台账号不受限。
另含 appid 全局唯一校验、代理商只能把商户开在自己名下、非平台账号不得改变商户归属。

## 4. 小程序代发布（后台发布/升级小程序）

**可行**，需接入**微信开放平台第三方平台**（自建「平台型」第三方平台，需 300 元认证与域名校验）。

流程：
1. 平台参数存 `sys_config`（`wx.open.*`，脚本已初始化），在「小程序平台配置」页面维护（见 4.1）。
2. 接收微信每 10 分钟推送的 `component_verify_ticket`（需常驻缓存，重启不丢，建议 Redis 持久化）。
3. 商户扫码授权 → 拿 `authorizer_refresh_token` 存 `biz_mp_auth`（**必须加密存储**）。
4. 平台维护统一代码模板（草稿箱 → 模板库 `templateId`）。
5. 后台一键操作，全程记录 `biz_mp_release`：
   `commit`（带 ext.json 注入各商户 appid/域名等差异）→ `get_qrcode` 体验版 →
   `submit_audit` 提审 → `release` 发布 → 必要时 `undocodeaudit`/`revertcoderelease` 回退。

### 4.2 ext.json 自动生成（已完成）

ext.json 不再手工填写，避免商户多时抄错 appid：

- 接口：`GET /biz/mprelease/extjson/{merchantId}`（`IMpReleaseService.buildExtJson`）。
- 数据来源：`extAppid` 取 `biz_merchant.appid`（商户管理 → 微信配置维护）；
  `ext.merchantId`/`ext.merchantName` 取商户记录；`ext.baseUrl` 取 `wx.open.apiBaseUrl`
  （在「小程序平台配置」页面维护）。
- 前端行为：代上传表单选择商户后自动填充（已手动改过的内容不静默覆盖），
  另提供「重新生成」按钮强制覆盖；提交前校验是否合法 JSON。
- 后端兜底：新增时 `extJson` 为空则自动生成，`templateId` 为空则取 `wx.open.templateId`，
  所以即使前端不传也能得到正确内容；商户未配 appid 时明确报错而非生成半成品。
- 小程序侧无需改动：`miniprogram7/utils/config.js` 已用 `getAccountInfoSync` 自取 appid，
  ext.json 只承担商户标识与接口域名的注入。

关键限制（需提前告知客户）：
- 每个小程序**必须自行完成主体注册与认证**，代发布不能免除主体资质。
- 提审由微信人工审核，**无法保证时效**，涉及团购/预约类目需补充资质。
- 模板升级是**逐个 appid 循环调用**，商户多时要做异步任务队列 + 失败重试（可挂 `ruoyi-quartz`）。
- 小程序代码里的 appid 相关差异只能通过 `ext.json` 注入，不能编译期写死。

对应权限：`biz:mprelease:auth/upload/audit/release/rollback`。
